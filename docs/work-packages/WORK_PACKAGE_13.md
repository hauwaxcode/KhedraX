# KhedraX Work Package #13
### Deployment Registry & Deployment Engine (non-producer) — Pharos first

Governing documents: `KHEDRAX_CONSTITUTION.md`, `SYSTEM_ARCHITECTURE.md`
(Deployment Engine and Registry System entries added/updated for this
package), `VERSIONING_POLICY.md`. **Targets: Architecture v1.x.** This
classification is load-bearing, not a formality — see §3 for exactly why
it qualifies, and treat any deviation from that reasoning during
implementation as a "stop and explain" trigger, the same as an engine
change would be in a registry-growth package.

This package resolves two things that were deliberately decided before
any code was written, not left implicit:

1. **Deployment Engine is not a producer.** It does not join the fixed
   `template → module → persona → prompt → memory → documentation`
   sequence. It is a new, optional, conditionally-invoked stage —
   architecturally a sibling of Packaging Engine, not a member of that
   sequence. This is what keeps this package v1.x under
   `VERSIONING_POLICY.md` §3, which specifically restricts "adding/removing
   a **producer** engine" — Deployment Engine is deliberately not one.
2. **KhedraX never executes a deployment itself.** Deployment Engine
   scaffolds a `deployment/` directory the generated project owns and runs
   independently — a deploy script, environment templates, secrets
   placeholders, monitoring/rollback documentation. Nothing about actually
   talking to Pharos's network, holding a wallet key, or performing a live
   deployment lives in KhedraX's own codebase. This preserves Constitution
   #14 (generated projects are standalone) and #15 (KhedraX generates
   software, it does not execute or host it) without amending either. The
   later CLI convenience (`khedrax deploy`, planned for a future package)
   will be a thin launcher that only ever runs the *generated project's
   own* script — do not build that launcher in this package; this package
   is scaffolding-only, per the roadmap's own sequencing.

---

## 1. Engineering Objective

Add a `deployments/` registry (mirroring the exact discovery pattern
`memoryBackends/` already established), a new **non-producer** Deployment
Engine invoked conditionally by Generation Engine only when
`dna.deployment.target` is set, and two real deployment targets: `pharos`
(the roadmap's named first target) and `local` (a safe, side-effect-free
target used for testing — real deployment validation against Pharos itself
is explicitly a later package's job, not this one's).

## 2. Why This Exists

The roadmap's long-term goal is deployable agents, not just generated
scaffolding. This package is the foundation: proving deployment targets
can be pure registry data (network config, wallet integration type,
required secrets, monitoring/rollback strategy — all declarative, no
different in kind from a persona or memory backend), consumed by a new
engine that doesn't disturb anything that already works.

## 3. Why This Is v1.x, Precisely

- The six producer engines' identity, membership, and invocation order are
  completely unchanged — they still run unconditionally, in the same
  order, for every project, exactly as before this package.
- No existing engine's ownership boundary changes.
- `AgentDNA.deployment` has been an empty-but-present top-level field
  since Work Package #1 (Constitution #9 already anticipated this) — this
  package gives it a concrete optional shape, the same additive-narrowing
  pattern Work Package #2 (persona) and #6 (memory) already used safely.
- A v1.0-generated project (with `deployment: {}`) remains fully valid —
  Deployment Engine is a no-op when `dna.deployment.target` is unset,
  which is every project generated by every prior work package.

If implementation reveals any of the above isn't actually true — e.g. if
Deployment Engine turns out to need to run *between* two existing
producers rather than after all of them — stop and report that
explicitly. That would change the classification, and this package
doesn't have authority to decide that silently.

## 4. Architecture Boundaries

- Deployment Engine reads only `dna.deployment` and the Registry System's
  `deployments/` snapshot — it does not read Module Engine's, Persona
  Engine's, or any producer's artifacts. A deploy script doesn't need to
  know which modules or persona were chosen; keep this engine decoupled.
- Deployment Engine runs in `generationEngine.ts` **after** the producer
  loop completes and **before** Packaging Engine's commit, and **only**
  when `dna.deployment?.target` is truthy. This is the one necessary,
  explicitly-scoped addition to Generation Engine's own orchestration code
  — narrower than Work Package #7's `khedraxRootDir` plumbing, and for the
  same kind of reason: a small, unavoidable wiring change to invoke a new
  stage, not a change to what any existing stage does.
- The scaffolded deploy script must be **real but honestly thin**
  (Constitution #10) — it should genuinely perform deployment *mechanics*
  it can actually do at generation time (validate required secrets are
  set in the environment, echo target-specific setup steps), while the
  actual "start the agent" command is a clearly-labeled placeholder — since
  no generated project has real runnable agent code yet (every module is
  scaffold-only). Do not write a script that pretends to do more than
  that; do not write a script that does nothing at all either.
- No network access at generation time. `pharos`'s descriptor contains
  configuration *about* Pharos (chain ID placeholder, required secret
  names), never a live credential or endpoint KhedraX itself would call.

## 6. Data Shapes

**`deployments/pharos/deployment.json`:**
```json
{
  "name": "pharos",
  "version": "1.0.0",
  "runtime": "node18",
  "network": { "chainId": "PHAROS_CHAIN_ID_PLACEHOLDER", "rpcUrlEnvVar": "PHAROS_RPC_URL" },
  "walletIntegration": { "type": "private-key-env", "secretEnvVar": "PHAROS_DEPLOYER_PRIVATE_KEY" },
  "secretsRequired": ["PHAROS_RPC_URL", "PHAROS_DEPLOYER_PRIVATE_KEY"],
  "monitoring": { "healthCheckPath": "/health", "logDestination": "stdout" },
  "rollback": { "strategy": "redeploy-previous-version" }
}
```

**`deployments/local/deployment.json`** (safe, side-effect-free, used for
testing — no real secrets, no real network):
```json
{
  "name": "local",
  "version": "1.0.0",
  "runtime": "node18",
  "network": { "chainId": null, "rpcUrlEnvVar": null },
  "walletIntegration": { "type": "none" },
  "secretsRequired": [],
  "monitoring": { "healthCheckPath": "/health", "logDestination": "stdout" },
  "rollback": { "strategy": "restart-process" }
}
```

**`AgentDNA.deployment` concrete shape** (was `Record<string, unknown>`,
now, additively):
```typescript
deployment: {
  target?: string;   // key into registry.deployments; optional
}
```

**`DeploymentDescriptor` (`src/registry/types.ts`):**
```typescript
export interface DeploymentDescriptor {
  name: string;
  version: string;
  runtime: string;
  network: { chainId: string | null; rpcUrlEnvVar: string | null };
  walletIntegration: { type: string; secretEnvVar?: string };
  secretsRequired: string[];
  monitoring: { healthCheckPath: string; logDestination: string };
  rollback: { strategy: string };
  templatesPath: string;  // synthesized by the loader, like modules' `path`
}
```

**Template files** — `deploy.sh` must genuinely check `secretsRequired`
against `process.env` (or shell equivalent) and fail with a clear message
if any are missing, before reaching a clearly-commented placeholder line
for the actual start command (e.g. `# TODO: replace with your agent's
actual start command`). `.env.example` lists each required secret with a
one-line comment. `README.md` documents the monitoring/rollback strategy
from the descriptor in human-readable prose (same rendering spirit as
Documentation Engine, but this is static template content per target, not
DNA-driven prose — keep it simple).

## 7. Deployment Engine Algorithm

1. If `dna.deployment?.target` is unset, do nothing — return
   `{ artifacts: { skipped: true } }` immediately.
2. Otherwise, look up `registry.deployments[target]` (already validated to
   exist by Validation Engine before Generation Engine ever runs — trust
   validation, don't defensively re-check).
3. Copy that target's `templates/` directory into
   `context.tempDir/deployment/` (overwriting Template Engine's static
   placeholder there, the same way Documentation Engine already overwrites
   the root README placeholder).
4. Substitute the descriptor's own data into the copied files where
   relevant (e.g. the `secretsRequired` list into `deploy.sh` and
   `.env.example` — don't hardcode Pharos-specific or Local-specific
   values into the engine code; read them from the descriptor).

## 8. Validation Addition

In `validateDna.ts`: if `dna.deployment.target` is set, it must exist in
`registry.deployments` — an error, not a warning, mirroring the exact
persona-preset and memory-backend validation pattern already established.

## 9. Required Tests

1. `deploymentRegistry.test.ts`: discovers both `pharos` and `local`;
   skips a malformed `deployment.json` the same way every other registry
   already does.
2. `deploymentEngine.test.ts`: `dna.deployment` unset → no-op, `deployment/`
   directory still contains only Template Engine's original scaffold;
   `dna.deployment.target: 'local'` → `deployment/` is replaced with
   `local`'s templates, `deploy.sh` contains the (empty, for `local`)
   secrets-check logic; `dna.deployment.target: 'pharos'` →
   `deploy.sh`/`​.env.example` correctly list `PHAROS_RPC_URL` and
   `PHAROS_DEPLOYER_PRIVATE_KEY`.
3. An unknown deployment target is rejected by validation before
   Deployment Engine (or any producer) ever runs — verify this the same
   way persona-preset and memory-backend rejection were verified (assert
   Deployment Engine is never invoked in this failure path).
4. Re-run the existing Generation Engine orchestration-order test
   unmodified — proving the six producers' order is untouched.

## 10. Acceptance Criteria

1. `khedrax create LocalBot --type basic --deployment local --force`
   succeeds and produces a `deployment/` directory with `local`'s
   scaffolded files. Paste the actual `deploy.sh` content.
2. `khedrax create PharosBot --type basic --deployment pharos --force`
   succeeds and produces `deployment/deploy.sh`/`.env.example` correctly
   referencing Pharos's required secrets. Paste the actual content.
3. `khedrax create MinimalBot --type basic --force` (no `--deployment`
   flag, the standing default case) produces **identical** output to
   before this package existed — `deployment/README.md` unchanged from
   Template Engine's original placeholder. This is the proof that
   opting out has zero effect, the actual point of §3's classification.
4. An unknown `--deployment nonexistent-target` is rejected by validation
   before any file is written.
5. `npm test` and `npm run typecheck` both pass — paste raw terminal
   output directly.
6. Zero changes to any producer engine (`templateEngine.ts`,
   `moduleEngine.ts`, `personaEngine.ts`, `promptEngine.ts`,
   `memoryEngine.ts`, `documentationEngine.ts`) or Packaging Engine —
   confirm by diffing them against the pre-package state.
7. `CHANGELOG.md` gets a new entry for this package. Before assuming the
   next version number, check what `SYSTEM_ARCHITECTURE.md`'s and
   `KHEDRAX_CONSTITUTION.md`'s current header versions actually say versus
   `CHANGELOG.md`'s most recent entry — Work Package #12 added a v1.2
   CHANGELOG entry but may not have bumped the two header files to match
   (verify this directly, don't assume either way). Reconcile any gap
   found, then add this package's own entry as the next version after
   whatever the correct current one turns out to be. Verify the file's

   no-line-over-2-leading-spaces check) before reporting this done, per
